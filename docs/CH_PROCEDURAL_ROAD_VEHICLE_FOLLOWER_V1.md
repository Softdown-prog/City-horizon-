# CH_PROCEDURAL_ROAD_VEHICLE_FOLLOWER_V1

## Purpose

Define the first logical vehicle-motion layer for City Horizon's elastic procedural roads without replacing `CH_ROAD_TRAFFIC_V1` yet.

The follower consumes the continuous `(x,y,z)` route generated by `CH_PROCEDURAL_ROAD_ROUTE_V1` and advances a logical vehicle by traveled world distance rather than by discrete road tiles.

## Source

- `src/procedural_road_vehicle_follower.h`
- integrated contract gate: `src/procedural_road_lane_connector_test.cpp`

## Core guarantees

- movement is distance-based over the sampled continuous route;
- position is interpolated in world `(x,y,z)`;
- heading is derived from the current route tangent;
- the returned forward vector is normalized;
- route distance never moves backwards;
- a vehicle reaches the exact route end and then stops;
- elevated ramps and viaducts preserve their authored `z` value;
- junction points can impose a lower speed cap than normal road lane points;
- left/right/U-turn connectors can impose a lower turn speed cap;
- this layer does not infer a connection from a geometric XY crossing;
- this layer does not change legacy tile traffic, save data, road occupancy or economy.

## Default motion values

The initial logical defaults intentionally mirror the conservative values already used by City Horizon road traffic where practical:

- cruise speed: `1.35` world units/s;
- acceleration: `1.10` world units/s²;
- braking: `2.75` world units/s²;
- junction speed: `0.85` world units/s;
- turning speed: `0.70` world units/s.

These values are tuning defaults, not a visual approval contract.

## Pose contract

`ProceduralRoadVehiclePose` exposes:

- `position` — current world position;
- `forward` — normalized 3D travel direction;
- `heading_radians` — XY heading for orienting a 2D runtime sprite;
- `speed` — current logical speed;
- `route_distance` / `route_length`;
- current route-point kind;
- current junction turn kind;
- `finished` state.

The renderer may quantize `heading_radians` to City Horizon's approved 2D vehicle directions while movement itself remains continuous.

## Migration boundary

`TrafficVehicleManager` remains the production fallback and continues consuming tile routes.

Do not remove or bypass that system until all of these have been proven:

1. procedural road visual proof passes at gameplay scale;
2. continuous route and follower gates compile and pass;
3. real vehicle sprites can consume the procedural pose without visual sliding;
4. car-to-car separation is implemented on continuous routes;
5. crosswalk/traffic-light stopping has a procedural equivalent;
6. save/load migration has a documented backward-compatible plan.

## Next step

The next bounded integration is a procedural traffic instance/adapter that converts a `ProceduralRoadVehiclePose` into the existing 2D `MobileEntityRenderData` direction/anchor model while preserving legacy traffic in parallel.
