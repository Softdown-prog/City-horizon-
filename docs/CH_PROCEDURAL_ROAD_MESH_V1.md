# CH_PROCEDURAL_ROAD_MESH_V1

## Purpose

`CH_PROCEDURAL_ROAD_MESH_V1` is the runtime-facing contract for elastic roads in City Horizon.

The game remains a 2D isometric city-builder. Terrain, buildings, vegetation, characters and the existing simulation continue to use the established SDL3/C++ 2D runtime. Only road geometry may opt into a lightweight 3D world representation `(x, y, z)` before being projected through the canonical `CH_CAMERA_V1` camera.

This is not a migration to a general-purpose 3D engine.

## Current stage

The implementation remains parallel to the legacy tile road system while the visual/editor proof is validated.

- `RoadManager` remains authoritative for current occupancy, construction cost, connectivity, pathfinding integration and saves.
- `RoadVisualCatalog` and the 16-mask PNG road renderer remain the production fallback.
- `RoadSplineSegment` describes one cubic Bezier centerline in world space.
- `RoadMeshBuilder` expands that centerline into a triangulated road ribbon with UV coordinates.
- `ch::world_to_screen_point(x, y, z, ...)` projects elevated geometry through the same 45-degree yaw / 30-degree elevation orthographic camera.
- `ch::screen_to_world_point(...)` is the continuous inverse ground projection used by road-editor gizmos; tile picking wraps this function and floors the result.
- `src/ch_render/procedural_road_renderer.h` is a thin SDL3 adapter that projects and submits a cached `RoadMesh` through `SDL_RenderGeometry`.
- `MapForge2ProceduralRoadPreview` now has two modes: deterministic PNG output when an output path is supplied, and an interactive pilot when launched without arguments.

No save-format or gameplay-topology migration is part of this stage.

## Geometry contract

A road segment is a cubic Bezier curve with four control points:

```text
start ---- control_a .... control_b ---- end
```

Each point carries `x`, `y` and `z` in world units. `x/y` use the same logical world axes as the existing grid. `z=0` lies on the ground plane. Positive `z` lifts the road toward the camera.

The mesh builder samples the curve, computes a planar tangent, offsets left/right by half the requested road width, then emits two triangles between consecutive sample pairs. Longitudinal UV distance follows the full 3D centerline length so textures remain stable on slopes.

The implementation supports:

- straight roads;
- arbitrary smooth curves;
- S-curves;
- ramps;
- elevated spans;
- geometry suitable for future bridges and viaducts.

Junction meshing, lane graphs, shoulders, curbs, guard rails, bridge decks/pillars and automatic intersection solving remain later layers.

## Camera and Z projection

The ground projection remains the existing 128x64 2:1 dimetric projection. For elevated geometry, one world unit of pure Z projects upward by `kWorldElevationPixelsPerUnit`, derived from the fixed 45-degree yaw / 30-degree elevation `CH_CAMERA_V1` contract.

Z does not alter logical tile picking or the existing ground-plane depth key in this stage. Elevated-road occlusion will receive its own explicit ordering contract when bridge/vehicle integration begins.

The continuous inverse projection lives in `src/ch_core/projection.*`; editor tools must use it instead of reimplementing the inverse transform locally. The project-centered `CH Math Worker` mirrors this canonical math for agent/tool batch calculations.

## CH Blender role

CH Blender remains an offline authoring tool and is not a runtime dependency.

It should author reusable source components such as:

- asphalt/material source;
- road cross-section profiles;
- curb profiles;
- sidewalks/shoulders;
- bridge deck side geometry;
- barriers and guard rails;
- support pillars;
- lane-marking source patterns.

Runtime curves are generated by the game from compact road graph/spline data. The game must not launch Blender to build a road while the player is playing.

## MapForge interactive pilot

Build/run `MapForge2ProceduralRoadPreview` without arguments to enter the interactive proof.

Controls:

- left-drag one of the four handles: move its `x/y` position continuously in world space;
- `PageUp` / `PageDown`: raise/lower the selected handle in `z` by 0.10 world units;
- hold `Shift` with `PageUp` / `PageDown`: use 0.25-unit elevation steps;
- `1`, `2`, `3`, `4`: inspect the same road under all four canonical camera quarter-turns;
- RMB/MMB drag: pan;
- mouse wheel: zoom;
- `R`: reset the pilot curve/camera;
- `Esc`: deselect the active handle.

Supplying an output path preserves deterministic headless capture:

```text
MapForge2ProceduralRoadPreview.exe out/procedural_road_preview.png
```

This pilot intentionally does not mutate scenario files yet. It exists to prove curve editing, canonical projection and elevation before the save/gameplay graph changes.

## Focused proof workflow

`.github/workflows/ch-procedural-road-proof.yml` is path-scoped to the procedural-road/math files. It runs the `CH Math Worker` self-test, builds only `MapForge2ProceduralRoadPreview`, renders the deterministic PNG and uploads the proof artifact.

If GitHub Actions creates a failed run with zero jobs, no compile/render step has executed; treat that as runner/Actions availability rather than evidence of a C++ failure.

## Target migration path

### Phase 1 - geometry proof

Implemented: cached Bezier road mesh, canonical Z projection, deterministic preview and math-worker support.

### Phase 2 - MapForge pilot (current)

Implemented in the focused preview: editable start/end points and Bezier handles, continuous XY movement, elevation editing, pan/zoom and four camera rotations. The next step is embedding this pilot into the main canonical MapForge viewport after the visual gate passes.

### Phase 3 - junctions

Introduce `RoadNode` + `RoadSegment` graph data and deterministic junction meshing for intersections, T-junctions, merges and roundabouts.

### Phase 4 - gameplay migration

Move vehicles from tile-center traversal to sampled lane centerlines. Keep building road-access semantics compatible by resolving spline/graph coverage back to the logical grid where needed.

### Phase 5 - elevation structures

Add bridge/viaduct support pieces, crossing rules, clearance validation and elevated depth/occlusion ordering.

## Non-goals

This contract does not:

- turn buildings or characters into live 3D models;
- replace the 2D renderer;
- require OpenGL, Unity or Unreal;
- remove existing PNG roads before the replacement path is proven;
- change the camera, tile scale or gameplay grid;
- make Blender a runtime dependency.

## First visual acceptance gate

The procedural system must not replace the legacy road renderer until a MapForge capture demonstrates, at gameplay scale:

- one continuous S-curve with no visible tile stepping;
- one straight-to-curve transition without cracks;
- one elevated ramp/span whose projection remains aligned with the 2D world;
- correct appearance under all four camera quarter-turns;
- handle editing that does not drift away from the canonical inverse projection;
- no regression to current tile-road gameplay when procedural mode is disabled.
